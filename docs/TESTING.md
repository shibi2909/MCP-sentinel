# Testing documentation

## 1. How to run

```powershell
cd C:\Users\dilba\mcp-sentinel\backend
.\.venv\Scripts\Activate.ps1
python -m pytest -v
```
The suite uses a temporary data folder and database (see `tests/conftest.py`), so it never
modifies the demo database. Last run on the development laptop: **58 passed** (≈10 s).

Frontend: `npm run build` (in `frontend/`) runs the TypeScript compiler in strict mode and the
production build.

## 2. Test inventory

### Unit tests – `tests/test_validation.py` (M4, 13 tests)
Clean input and arithmetic are not flagged; path traversal (Unix and Windows), command chaining
and substitution, SQL injection (tautology, UNION SELECT), schema violations, missing required
fields and oversized payloads are critical; prompt injection is high but not critical; nested
values are inspected.

### Unit tests – `tests/test_core_modules.py` (18 tests)
* M3: canonical hash independent of key order; detects description change; ignores non-contract metadata.
* M6: rule score bounded and explained; configuration A never calls ML; B combines 0.6/0.4.
* M7: critical violation is BLOCK even with score 0; threshold bands; bulk + high sensitivity → approval;
  LOCKDOWN only escalates; `escalate` is monotonic.
* Controller: bounded for 5 000 random (including out-of-range) inputs; tightens to LOCKDOWN
  under sustained attack and returns to NORMAL; anti-windup bounds recovery time.
* M8: secrets detected and redacted; prompt injection / exfiltration detected; normal output clean.

### End-to-end tests – `tests/test_api.py` (27 tests)
Run through the HTTP API with the real gateway and in-process MCP servers:
* M2: wrong password 401, missing/invalid token 401, viewer and analyst role restrictions (403).
* **All 7 demo scenarios** individually, and all 7 run twice in sequence (controller state
  accumulates between scenarios, so expected decisions must hold in a "dirty" state too).
* M1: `tools/list` respects agent scope; `tools/call` returns MCP result with Sentinel metadata;
  missing key → −32001; invalid JSON-RPC → −32600.
* M7: approval executes the tool and cannot be approved twice (409); approval is refused if the
  tool definition changes while waiting (time-of-check/time-of-use protection).
* M3: integrity check fails after tampering and passes after restore.
* M9: chain valid → tampered record detected at the exact sequence number → restored → valid;
  every decision produces an audit record.
* M10 data: dashboard totals equal the requests actually made.
* Configuration switch to A disables ML scoring.
* M5: safe computation completes; file escape and process spawn are blocked.

## 4. Experiment method (configurations A, B, C)

`python -m app.experiments` (or **Experiments → Run experiment** in the dashboard):
* Deterministic trace (seed 2026): 120 normal requests (3 % malicious) → 120 attack-campaign
  requests (45 % malicious) → 120 recovery requests (3 % malicious).
* Each request has real arguments and goes through the real validation, risk, policy and
  controller code; only the network call to the MCP server is skipped.
* "Caught" = BLOCK or REQUIRE_APPROVAL. Metrics: detection rate, false-positive rate, precision,
  F1, per phase, and missed attack kinds.
* Robustness: means over seeds 2026, 7, 99, 123, 555; controller gain sensitivity analysis.
* Results are written to `docs/results/experiment_results.md` / `.json`. **Use those files (or the
  dashboard) as the source of any numbers in the report** – do not copy numbers from elsewhere.

Observed on the development laptop (seed 2026, generated by the code, see the results file):
configuration C raised the detection rate compared with A and B without increasing the
false-positive rate on this seed; over 5 seeds C had the highest mean detection rate with a
false-positive rate similar to A. More aggressive controller gains catch more attacks but
produce more false positives (trade-off table in the results file). Attacks with no input
signal (low-and-slow enumeration) were missed by all three configurations.
